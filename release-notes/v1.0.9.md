# Claude Code Heihei v1.0.9

本版本对「主管自己干活」问题做**机制级根治**：角色边界不再依赖提示词自觉，而是工具面结构性收权。

## 主管会话工具收权（根治"顺手代劳"）

- **背景**：v1.0.7 已在履新消息写明"第一反应是拆解派活"，但提示词是软约束——延续对话的旧上下文会压过新规则（09-11 实测复发：主管在延续对话里亲自改文件干活），且模型对"小任务"有强烈的顺手代劳倾向。
- **机制**：主管会话的 **Edit / Write / NotebookEdit 被结构性拒绝**，越权时返回带派活指引的拒绝文本（而非报错），模型自然转向正确的协作通道。服务端按花名册自动注入主管标记，无需配置。
- **放行例外**：派活协议自身的写入不受影响——`.dispatch-payload.json`、`report-payload.json`、`.heihei/dispatch/` 信箱文件照常可写（严格白名单，相似文件名不放行）。
- **豁免通道**：确需主管亲自执行时，在会话右键「协作设置…」取消主管身份即可恢复完整工具权限。

## 存量主管一次性触达

- 履新消息只在首次任命时注入，老主管的延续对话永远收不到升级后的规则。服务端现在**启动时对全部已登记主管投递一次协议更新通知**（硬规则全文），marker 文件保证跨重启幂等——你现有的主管会话升级后重启应用即可收到。

## 指令歧义规范

- 协议新增：用户说"你来实施 / 你直接干"这类模糊指令时，主管**默认理解为"由你安排实施"（派活）**；只有明确说"你亲自写/亲手改"才亲自做，拿不准先确认一句——修复"你规划下直接干活吧"被理解成主管亲自干的歧义场景。

## 升级说明

- 无破坏性变更。升级后重启应用：存量主管收到协议更新通知；新 appoint 的主管自动带收权标记；员工会话不受任何影响。
