# Claude Code Heihei v1.7.3

**清掉一批「已查实、暂未修」的缺陷**：五条登记缺陷修掉**四条**——两处会让会话**静默挂死**的文件操作、一处永久转圈的协作弹窗、一处会毁掉整份台账的脏行、一处隔离实例读错实例的端口路径；第五条（turn-checkpoints 慢点）经实测把「O(n²)」**证伪**、成因仍未定，**带数据挂档、本版未修**。另把「请求超时」与「业务失败」在界面上**区分开**。**无破坏性变更**。

## 修复：五条登记缺陷中的四条

### 1. Bun 的 `truncate` 永不返回 → 两处产品路径改「重写语义」

- **现象**：走到任一条用 `truncate` 的路径，`await` **永不返回**——不报错、不抛异常、也不自愈，表现为**静默挂死**。
- **根因（后端探针 9/9 实证）**：`fs.truncate` / `FileHandle.truncate` / `fs.ftruncate`（含 sync）在**缩短、等长、变长三个方向全部不返回**，三种 API 无差别 ⇒ 缺陷在底层 syscall 封装，**「换个 API 绕开」不可行**。
- **受影响的两处产品路径**：
  - `src/history.ts`（提示历史写入器的**回滚分支**）：原 `await truncate(...)` 永不返回 ⇒ 其 `catch` 兜底（毒化标记）**永远不执行** ⇒ 回滚静默挂死；
  - `src/utils/sessionStorage.ts`（**按 uuid 移除单条会话**）：原「定位行 + truncate」在**两个分支都会出事**——删**最后一条**直接挂死；删中间条则 truncate 挂住、补尾部永不执行 ⇒ **尾部永久丢失**。
- **修法**：两处都改为**重写语义**——把要保留的内容拼好后整体写回（写回天然截断，字节等价），彻底绕开 `truncate`。新增用例覆盖「删末条 / 删中间条」两种情形（结果字节等价）。
- **附带加固（独立审查发现）**：上述重写路径用 `Buffer.allocUnsafe(...)` 且未检查 `read` 的实际读取字节数——**与 CLI 子进程并发追加时可能「短读」**，把未初始化的堆内存写回用户转录（既污染数据、又泄露内存内容）。已加**一行守卫：短读即放弃本次删除**（删除属清理动作，放弃无害，且不增净行数）；快路径同时补上与慢路径同款的**大小上限**，避免大转录下的读写尖峰。

### 2. 协作设置弹窗对「不在花名册的会话」永久转圈

- **现象**：对**不在花名册里的会话**打开「协作设置…」，弹窗**永久停在加载态**，无失败态、无超时、无重试，提交按钮一并锁死（隔离演示实例观察 25 秒不消失）。
- **根因**：原判断「编辑模式 && 未读到该会话」**无法区分**「花名册**还没加载完**」与「花名册加载完了、**确实没这条**」——后者恒为真 ⇒ 永远停在加载态。
- **修法**：引入三态（**加载中 / 就绪 / 不在花名册**）：拉取完成后仍无此条，则给出**明确的失败提示 + 重试按钮**；该状态下提交按钮同样锁死（避免空表单被误提交覆盖原身份）。五语言各补一条文案，新增组件测试。

### 3. 端口文件读写两侧统一跟随配置目录（隔离实例不再污染 / 错读）

- **背景**：端口发现文件（`desktop-server.json`）此前固定在 `~/.claude/cc-heihei`，配置目录环境变量不参与 ⇒ 跑一个隔离实例会**覆盖真实应用的端口记录**，任何读它的工具（员工汇报、CLI 投递）会打到**错实例**。
- **修法（本版补齐两侧）**：
  - **写侧 / 默认目录**：默认路径改用「配置目录优先」的解析，隔离实例落在自己的配置目录内；**显式传入 home 的既有契约不变**。
  - **读侧**：独立实测发现读侧此前**没跟着改**（仍以 home 为基准）——隔离实例**读不到自己的**端口文件、回落拿到**真实应用的地址**。本版把两处读取方一并改为同一解析，并补测试**锁死「读侧确实接上了」**。
- **兼容性**：未设该环境变量时解析结果与旧写法**逐字相同** ⇒ 真实用户零影响。

### 4. 台账 replay 缺字段行归一为 `[]`

- **现象**：任务台账里只要出现一行**缺 `deliverables` / `history` 字段**的数据（手写行、旧版本写的行），会让**整份台账加载失败**，而不是只跳过这一行。
- **更正说明（如实）**：复核发现「坏 JSON 行的隔离跳过」**早已存在**；真正的缺口是 **created 分支没有做字段归一**——缺字段的行照旧入账，之后读路径展开时才抛错。
- **修法**：缺失字段统一 `?? []` 兜底 + 入口归一，并对「发生归一的坏行」记一条诊断（**可观测、不静默**）；与同模块对旧数据兼容的既有口径保持一致。新增用例覆盖。

### 5. turn-checkpoints 慢点：**「O(n²)」已证伪，成因未定**（本版未修）

- **背景**：上一版把「客户端 `Request timed out after 320s`」的根因候选指向某内部 checkpoint 拉取的**结构性 O(m·n)**。
- **本版实测结论**：
  - 三个真实会话（6.6k / 12.9k / 20.3k 行）只读副本实测 **2.1s / 70.7s / 54.5s**——**中档比大档还慢（非单调）**，且小→中 checkpoint 数只 +4% 而耗时 ×34 ⇒ **与规模、条目数均无关**，**复杂度假设被证伪**；同测另一接口 258/376/647ms 呈 ≈O(n) 作对照；
  - 同一份 83MB 转录**四次实测 4.1 / 54.5 / 68.8 / 70.7 秒（差约 17×）** ⇒ **不是稳定的算法复杂度问题**，更像**外部状态相关**（磁盘 / 页缓存 / 内存压力、JIT / GC 状态）；
  - CPU profiler 曾在**慢跑**里看到 82.9% 采样落在运行时正则引擎，但逐正则微探针实测三条候选正则合计仅 **≈0.1%**，且**快跑里该热点不出现** ⇒ 该「正则热点」**可能是果而非因**（推断，未证实）。
- **状态**：**成因未定、修法未落地、本版零代码改动**——**带数据挂档**；下一步需**多次采样 + 记录同刻系统状态**继续分诊。

## 衍生修复

- **「320 秒超时」不再呈现为业务失败**：`Request timed out after 320s` 此前被当普通错误弹红条，暗示「失败 / 重试」；实际它只断了连接、**业务仍在后台跑**。现在超时文案改为**「连接已超时；任务可能仍在后台运行，稍后刷新即可查看结果」**，turn-change 错误条在超时态改用**中性提示条**（而非红色失败条），并给了「刷新查看」的出路（五语言同步）。
- **409 跨项目派活文案的正则边界**：已知服务端错误串的映射正则补回了**词边界 `\b`**（此前是前缀匹配），使这条业务错误串与相似串的区分更精确。
- **CI 红灯：两笔测试侧修复**（改动只在测试与断言，不碰产品行为）：
  - `dispatch-mailbox` 用例在 CI 上因 **Windows `%TEMP%` 的 8.3 短路径**（如 `RUNNER~1`）导致路径归一化不识别、台账过滤出 0 条——改用 `realpath` 后的规范路径；
  - `MessageList` 的 `selectionchange` 用例在慢机上因**两帧 rAF 早于处理完成**而同步查询不到按钮——改为**带超时的显式异步查询**。
